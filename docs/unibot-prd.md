## 一、产品概述

### 1.1 产品定位

Unibot 是一个 **AI-Native 交互平台**——以 Chatbot 为入口，用户通过自然语言对话完成各类任务。平台由两层能力构成：

1. **Unibot Host 基础对话能力**：Host 内置 Agent Loop、LLM 调用、上下文管理和工具路由能力，能够理解用户意图、回答问题、执行基础任务。即使不安装任何外部 App，Unibot 也能作为完整的 Chatbot 正常使用。
2. **系统内置 App**（`unibot-assistant`）：以标准 AINA 形态暴露 Host 自身的系统管理工具和系统 Widget（如应用列表、Session 管理入口、`sys.*` 交互），但不承接普通文本对话本身。
3. **外部扩展 App**（AINA 协议注册）：提供领域能力（设计本体、管理记忆、审批流程等），扩展 Host 可路由的工具范围。

类比：Unibot 像 iPhone——开机就有系统级 Siri 能力可以对话和调度工具；内置系统 App 提供设置、应用列表等系统入口；安装 App 后才有拍照、导航、支付等扩展能力。

### 1.2 核心用户价值

| 用户角色 | 价值 |
|---------|------|
| **管理员** | 配置系统默认 LLM / MCP 连接，安装/卸载 App，编排 Skill/Playbook，封装领域知识，管理平台全部能力 |
| **普通用户** | 通过 Chatbot 完成各类任务；可配置个人 LLM Provider（按用户隔离），未配置时使用系统默认模型 |

### 1.3 产品形态

- **Web 应用**（浏览器直接访问，零安装）
- 主界面是一个 **Chatbot**，作为所有交互的统一入口
- Host 提供通用对话能力，无需安装任何外部 App 即可正常使用
- 内置系统 App `unibot-assistant` 提供系统管理工具和系统 Widget
- 安装扩展 App 后，Host 可路由调用扩展 App 的工具，能力自动增强
- 左侧面板管理会话和任务，中间/右侧是对话和可视化区域

### 1.4 内置扩展 AINA

Unibot 附带以下内置扩展 AINA，作为系统推荐的标准能力扩展（非UniBot模块核心功能需求，可独立部署和升级）：

| AINA | 说明                                                         |
|------|------------------------------------------------------------|
| **memory** | 将对话中产生的知识结构化持久化，每轮对话时按需检索注入，使 Agent 具备跨会话的持续认知能力，而不依赖长对话历史 |
| **builder** | 提供 AINA 的创建、调试、发布能力，管理员按照步骤操作即可构建和发布新的 AINA                |

> 内置 AINA 遵循与外部 AINA 完全相同的协议，系统对其无特殊依赖。即使不部署任何内置 AINA，Unibot 核心功能仍可正常运行。

## 二、核心用户场景 (Scenarios)

> 本章节依据 CDASE 规范，定义了驱动 Unibot 产品设计的 5 个核心业务场景。所有后续的功能设计 (Feature) 均从此处的 SCN 推导而来。

### SCN-001：用户的日常通用对话问答 (General Chat)

**1. 背景**
用户需要解答问题、搜索信息或生成文本，不需要特定复杂的界面，期望获得快速准确的自然语言响应。

**2. 核心流程**
1. 用户在主会话 (main session) 输入自然语言指令。
2. Host Agent Loop 直接处理通用对话意图，并在需要时调用已注册工具。
3. AI 生成回复，可能内嵌轻量级卡片 (Inline Card) 辅助展示（如选项、摘要）。
4. 用户阅读后继续多轮对话。

**3. 预期结果**
用户获得快速、准确的文本与内嵌卡片响应，对话历史持久化留存在独立的主会话中。

**4. 约束与规则**
- 主会话 (main) 永远不可删除，但支持一键清空历史。
- 每个对话 session 的上下文必须完全隔离。
- Inline Card 渲染不应阻塞用户的持续输入。

**5. 非功能需求 (NFR)**
- **性能**: 流式响应延迟要求——首 token ≤ 1s，流式 chunk 间隔 ≤ 100ms。

### SCN-002：基于画布的复杂富交互 (Canvas Workspace)

**1. 背景**
用户在进行复杂任务（如编辑长文、管理表格数据、可视化大纲）时，纯文本对话效率太低，需要全屏的、可直接操作的可视化工作区。

**2. 核心流程**
1. 用户下达涉及复杂信息处理的指令。
2. 工具响应携带 `canvas.open` 指令。
3. 界面自动切换为三栏布局 (Canvas Mode)：左侧导航收起，中间展示 Canvas，右侧保留窄对话框。
4. 用户在 Canvas 内进行 UI 交互（点击、编辑等），触发 Widget 直调工具 (ToolProxy)。
5. 界面根据返回数据进行 `patch` 增量或 `replace` 全量更新。
6. 任务完成，自动或手动调用 `close` 指令退出 Canvas，恢复常规双栏对话。

**3. 预期结果**
用户的复杂操作在得到直观界面反馈的同时，不丢失与 AI 的对话上下文（右侧栏）。

**4. 约束与规则**
- Widget 直调必须沿用当前 session，不能创建新会话，以保证数据流转一致性。
- Canvas 内的导航栈需支持后退操作。
- 当工具响应同时包含 html_widget (Inline Card) 和 canvas 时，优先展示内嵌卡片。

### SCN-003：异步长任务与外部事件跟进 (Task & Event Handling)

**1. 背景**
AI 执行某个任务需要很长时间（如批量处理大量数据），或者外部系统（如 CI/CD、审批流）产生了事件推送，用户不能一直停留在当前对话等待，但需要追踪进度并进行关键节点的确认。

**2. 核心流程**
1. 用户触发耗时操作，或系统接收到外部 Webhook Event。
2. 左侧“待办”栏出现新条目（Task 或 Event Session）。
3. 用户可离开当前页面，去处理其他对话。
4. 若任务执行到需人工确认节点（如调用 `sys.confirm` 或 `sys.prompt`），在待办栏高亮提示。
5. 用户点击待办条目，进入该独立任务的对话上下文，通过系统确认交互覆盖层完成确认操作。
6. 任务彻底结束，条目从待办栏自动归档消失。

**3. 预期结果**
长时间任务在后台静默运行不阻塞前台主要操作；外部事件和阻断性系统交互（系统确认框、密码输入）得以妥善流转和呈现。

**4. 约束与规则**
- 标记为紧急 (`priority: URGENT`) 的事件必须立即弹出打断当前流程，不等用户点击。
- 每个 Task 和 Event 都享有独立的 Session 隔离上下文。

### SCN-004：领域能力的扩展与使用 (App Ecosystem)

**1. 背景**
默认的通用能力无法满足特定业务（如设计本体管理、ERP 审批等），平台需要接入和管理外部独立 App 以扩展能力边界。

**2. 核心流程**
1. 管理员安装第三方扩展 App (符合 AINA 协议)。
2. 普通用户在会话中触发领域相关意图。
3. Host Agent Loop 智能路由调用已注册的扩展工具。
4. 或者，用户在应用列表主动点击 App 入口，进入该 App 专属的工作台 (App Session) 进行交互。

**3. 预期结果**
平台能力得到动态扩展，且普通用户的交互入口保持极致的简洁，App 工作台之间的上下文完全隔离。

**4. 约束与规则**
- 系统级管理配置（MCP、安装/卸载 App、系统模型）与普通用户隔离。
- 普通用户可自主启用/禁用已注册的 App，定制个人可用 App 列表。
- 支持同一 App 单实例或多实例工作台。

### SCN-005：跨会话的持续认知累积 (Continuous Memory)

**1. 背景**
用户希望 AI 能记住之前的偏好或重要知识（如项目背景、特定命名习惯），不需要在每次新建对话时枯燥地重复交代背景。

**2. 核心流程**
1. 每轮对话结束后，Host 触发后置钩子 `post_turn`。
2. 记忆插件异步分析并提取结构化知识到 MemoryStore，执行记忆固化（不阻塞响应）。
3. 用户隔日新建 session 发起对话。
4. Host 触发前置钩子 `auto_pre_turn`，按照用户本次意图检索相关历史记忆。
5. 提取的记忆组装为 System Prompt 注入，AI 根据历史积累的知识作答。

**3. 预期结果**
AI 表现出跨越单次会话生命周期的认知一致性，且不依赖超长上下文 token 堆叠，极大提升用户体验。

**4. 约束与规则**
- 无记忆扩展注册时，主系统必须平滑降级（如默认取最近 30 轮记录作为兜底）。
- 记忆的加载与固化应使用标准化响应与薄壳设计，主系统 (Host) 不耦合具体的记忆数据库实现。
- 当有多个 Memory 扩展时，Host 需提供统一的冲突和冗余合并机制。

### SCN-006：对话与 App 中的文件附件流转 (File Attachments)

**1. 背景**
用户在对话、Canvas 或 App 工作台中需要上传图片、文档、表格等文件，让 LLM 或 AINA App 读取、分析、转换或作为工具输入。文件不能直接塞进普通 JSON 工具调用，也不能无鉴权暴露给外部 App。

**2. 核心流程**
1. 用户在对话输入区、Canvas Widget 或 App 工作台中选择文件上传。
2. Host File Service 接收文件，完成类型、大小和权限校验，存储到本地磁盘或对象存储。
3. Host 返回 `file_id`，并将文件与当前 user/session/message 绑定。
4. 当 LLM 或 AINA Tool 需要消费文件时，Host 将文件转为 `file_ref` 引用，包含短效签名 URL、`mime_type`、`size` 等元信息。
5. AINA App 通过签名 URL 在有效期内回源下载文件；Host 校验 token、用户身份和访问范围。
6. 当 Session 删除、归档清理或文件过期时，Host 根据生命周期策略清理关联文件。

**3. 预期结果**
用户可以安全地上传和使用文件；Host 不把大文件塞进消息历史或工具 JSON，而是通过标准文件引用在 LLM、Widget、AINA App 之间流转。

**4. 约束与规则**
- 文件下载 URL 必须短效、带签名，并限制用户/Session 范围。
- AINA 工具调用默认使用文件引用模式，不直接传输二进制。
- 图片类文件在多模态模型场景下可由 Host 转为 LLM 所需的 `image_url` 或 base64 data URI。
- 文件生命周期必须与 Session 生命周期、用户权限和存储配额联动。

| 功能 ID | 功能描述 | 优先级 |
|---------|---------|--------|
| FTR-001-01 | 用户可创建新对话 session，与 LLM 进行多轮对话 | P0 |
| FTR-001-02 | Host 基础对话能力随系统启动可用；内置系统 App `unibot-assistant` 自动注册系统工具 | P0 |

## 四、交互模式总结

| 模式 | 触发条件 | Session | 用户视角分类 | 说明 |
|------|---------|---------|------------|------|
| 1. 纯对话 | LLM 纯文本回复 | 当前 | 对话 | 默认模式 |
| 2. Canvas | Tool 响应含 canvas.open | 当前（视图层） | 对话 | 全屏可视化 + 窄对话 |
| 3. Inline Card | Tool 响应含 html_widget | 当前 | 对话 | 对话流内嵌卡片 |
| 4. Widget 直调 | Canvas 内按钮点击 | 当前 | 对话 | 绕过 LLM，确定性操作 |
| 5. Task | LLM/用户发起长任务 | 独立 Task Session | 待办 | 异步执行，后台运行 |
| 6. Event | 外部系统推送事件 | 独立 Event Session | 待办 | 事件响应，与 Task 同管理 |
| 7. File Attachment | 用户上传或 Widget 产生文件 | 当前/关联 Session | 对话/待办 | Host 保存文件并以 `file_ref` 方式传递给 LLM 或 AINA App |

## 五、非功能需求总结 (NFR)

> 除各 Scenario 内部定义的核心 NFR 外，平台的通用技术要求如下：

| ID | 需求 | 目标 |
|----|------|------|
| NFR-01 | 前端兼容性 | 现代浏览器（Chrome/Firefox/Edge/Safari 最新版） |
| NFR-02 | 部署方式 | 单进程 Web 服务，零外部依赖（除 PostgreSQL 和 App 进程） |
| NFR-03 | 多 LLM Provider | 支持 DeepSeek、OpenAI、Ollama 等 100+ provider 切换 |
| NFR-04 | 数据持久化 | Session 元数据和消息历史持久化到 PostgreSQL，重启后可恢复 |
| NFR-05 | App 扩展性 | 动态安装/卸载 App，Host 代码零改动 |

## 六、迭代规划与依赖拆分 (Milestones)

基于功能模块的技术依赖关系（如：前端状态依赖 SSE、Task 依赖异步执行模型），对迭代阶段进行如下拆分：

### Milestone 1: 核心引擎与纯文本对话 (Foundation)
- **目标**：搭建底层框架（FastAPI + LLM 防腐层 + DB 双键隔离），跑通基础纯文本对话流。
- **涵盖功能**：
  - FTR-001 系列（对话与会话管理核心）
  - FTR-004 系列（基础系统配置与内置系统 App `unibot-assistant` 注册骨架）

### Milestone 2: 基础富交互 (Basic Rich UI)
- **目标**：跑通 AINA 协议工具调用和轻量级 UI，不涉及复杂状态和三栏布局。
- **涵盖功能**：
  - FTR-001-08 / 09 / 10（Inline Card 内嵌卡片）
  - FTR-003-06 ~ 11（`sys.confirm` 等系统确认模态交互）

### Milestone 3: 可视化画布与直调 (Canvas & ToolProxy)
- **目标**：实现复杂的三栏布局、视图栈及脱离 LLM 的旁路调用。
- **涵盖功能**：
  - FTR-002 系列（Canvas 基础框架、Patch 增量更新、多视图栈及 Widget 直调）
- **技术依赖**：需完善 Widget 状态（`__widget_state`）持久化机制以支持刷新回放。
  - 若 Widget 支持上传文件，则依赖 FTR-006 的文件上传和 `file_ref` 能力。

### Milestone 4: 长任务与事件驱动 (Async Operations)
- **目标**：支持后台长时间任务脱离单次 HTTP SSE 生命周期。
- **涵盖功能**：
  - FTR-003-01 ~ 05（Task Panel、Task / Event Session 隔离上下文）
- **技术依赖**：底层的异步执行与状态推送（进度条流式下发）。

### Milestone 5: 认知、扩展与生态 (Memory & Ecosystem)
- **目标**：实现跨会话持续认知及更复杂的插件系统连接。
- **涵盖功能**：
  - FTR-005 系列（Memory 预加载与异步固化集成）
  - Skill 渐进披露（Router 路由拦截）
  - MCP Server 协议打通与工具合并
  - FTR-006 系列（文件上传、签名 URL、AINA 文件引用协议）
